## 1. What `Extends` actually does

A block may declare:

```xml
<property name="Extends" value="ParentBlockName" param1="PropA,PropB,ClassName" />
```

Load order in `BlocksFromXml.ParseBlock`:

1. Find the `Extends` property (if any).
2. `CreateProperties(parentName, param1)`:
   - Look up the **already-loaded** parent `Block` by name.
   - `CopyFrom(parent.Properties, exclusions)`.
3. `LoadProperties` — apply **this** block’s `<property>` / `<array>` nodes (child wins on same key).
4. Build the `Block` instance from the merged properties.
5. Parse this block’s `<drop>` nodes.
6. Unless `<dropextendsoff />` is present, `CopyDroppedFrom(parent)` for drops.

### Critical constraints

| Rule | Why |
|---|---|
| Parent must appear **earlier** in XML than the child | `Block.GetBlockByName` must succeed at parse time |
| Multi-level works via **resolved parent snapshot** | Child copies parent’s *already merged* `Properties` + drops |
| `Extends` itself is kept as a property on the child | Used later for drop inheritance / tooling |

There is no runtime “prototype chain.” Flattening is exactly what the engine does at load.

## 2. `param1` on `Extends` = exclusion list (NOT include list)

```csharp
// BlocksFromXml.CreateProperties
HashSet<string> hashSet = new HashSet<string> { Block.PropCreativeMode }; // always exclude
// then split Extends.param1 by comma and add each trimmed name
dynamicProperties.CopyFrom(blockByName.Properties, hashSet);
```

So:

```xml
param1="CustomIcon,DescriptionKey,DowngradeBlock"
```

means: **do not inherit** those properties from the parent.

### Always excluded (hardcoded)

- `CreativeMode` — never inherited. Comment in vanilla `blocks.xml`: intentional.
- Default `EnumCreativeMode` if unset = `All` (enum 0). That shows in creative for every mode filter.
- Therefore any child that must be hidden / Dev-only / Player-only **must set `CreativeMode` itself**.

### What can be excluded

1. Flat properties: `CustomIcon`, `DescriptionKey`, `Material`, `DowngradeBlock`, …
2. Whole property **classes**: `RepairItems`, `UpgradeBlock`, `CompositeFeatures`, …
3. Nested class keys via `ClassName.ChildKey` (see `GetNestedExclusions` / `copyKey`):
   - Excluding `RepairItems` skips the whole class.
   - Excluding `RepairItems.resourceWood` skips only that nested entry (prefix rules apply).

### Two different meanings of `param1`

| Location | Meaning |
|---|---|
| On `name="Extends"` | Inheritance **exclusion** list |
| On any other property (`Model`, `ImposterExchange`, `CanPickup`, …) | Property-specific secondary arg stored in `DynamicProperties.Params1` |

Do not confuse them when flattening.

## 3. `dropextendsoff` and drop merge

```xml
<dropextendsoff />
<drop event="Destroy" count="0" />
```

Engine:

1. Always parse the child’s own `<drop>` elements first.
2. If **no** `dropextendsoff`, call `CopyDroppedFrom(parent)`.
3. `CopyDroppedFrom` merges parent drops **per event**, adding only entries whose `name` is not already present on the child for that event.

Implications:

- Child drops win for the same drop `name` under the same event.
- Parent can still contribute *additional* differently-named drops.
- `dropextendsoff` = “use only my drops; ignore parent drops entirely.”
- You **cannot** exclude drops via `Extends param1`. Vanilla docs note that; the game later added `dropextendsoff` as the kill-switch.
- Multi-level: grandchild inherits the **parent’s final drop list** (which already includes grandparent unless parent used `dropextendsoff`).

Classic color / special terrain pattern:

```xml
<block name="terrDirtTwitch">
  <property name="Extends" value="terrDirt" />
  <property name="CreativeMode" value="None" />
  <property name="CustomIcon" value="terrDirt" />
  <property name="CustomIconTint" value="6441A5" />
  <dropextendsoff />
  <drop event="Destroy" count="0" />
  ...
</block>
```

## 4. Multi-level extends — practical model

```
A (base)  →  B extends A  →  C extends B
```

At load:

- `B.Properties` = A.props − (CreativeMode + B.param1) ∪ B.props
- `B.drops` = B.drops ∪ (A.drops unless B.dropextendsoff)
- `C.Properties` = B.Properties − (CreativeMode + C.param1) ∪ C.props
- `C.drops` = C.drops ∪ (B.drops unless C.dropextendsoff)

`param1` exclusions apply **only to that child’s copy from its direct parent**. They are not sticky for grandchildren unless the intermediate also excluded / overwrote them.

Example: if `B` inherits `CustomIcon` from `A`, and `C` does not exclude it, `C` still gets `A`’s icon through `B`’s resolved properties.

## 5. Color / tint “thin” extends (decoration pattern)

Vanilla pattern for recolors (doors, safes, lanterns):

```xml
<block name="ironDoorBrown">
  <property name="Extends" value="ironDoorWhite" />
  <property name="CustomIcon" value="ironDoorWhite" />
  <property name="CustomIconTint" value="7E786E" />
  <property name="TintColor" value="7E786E" />
  <property name="SortOrder2" value="0001" />
</block>
```

Notes:

- Same mesh/model as parent; only tint + sort (+ sometimes DowngradeBlock) change.
- `CustomIcon` points at the **base icon sprite name**, not the new block name.
- `CustomIconTint` / `TintColor` are hex RGB (no `#`).
- Often **no** `CreativeMode` on these children → default `All` (visible). Parent also often omits it.
- When parent has an icon you must *not* keep (wrong sprite for open/closed, helper, etc.), exclude with `param1="CustomIcon"` and set a new one.

## 6. `CustomIcon` for new / mod blocks

```csharp
// Block.GetIconName
return CustomIcon ?? GetBlockName();
```

- If `CustomIcon` is unset, the game looks for an ItemIcons sprite named **exactly like the block**.
- New mod block names almost never have a matching vanilla sprite → missing / pink icon unless you:
  1. Set `CustomIcon` to an existing sprite name, and/or
  2. Ship `UI/ItemIcons/<BlockName>.png` (and atlas/UI resources as required by your pipeline), and/or
  3. Tint an existing icon with `CustomIconTint`.

For flattened decoration clones, always set `CustomIcon` (usually to the vanilla source block / model icon). Helpers often also set `ItemTypeIcon` (e.g. `all_blocks`).

## 7. `SortOrder1` / `SortOrder2` (creative lists + helpers)

```csharp
SortOrder = Properties.GetString("SortOrder1") + Properties.GetString("SortOrder2");
// creative list:
string.CompareOrdinal(a.SortOrder, b.SortOrder); // then Id tie-break
```

### Rules

- Sort key is the **string concatenation** of `SortOrder1` + `SortOrder2`.
- Comparison is **ordinal string**, not numeric. Zero-padding matters (`0009` < `0010`; `100` < `99` as strings — pad!).
- Missing parts become `""` via `GetString`.
- Letter prefixes create buckets: `0000…` terrain, `B###` building/loot, `M###` masters, `S###` shapes, `U###` player helpers / variant helpers, etc.
- Within a family, keep **shared `SortOrder1`**, vary **`SortOrder2`** (`0000`, `0001`, `0100`…).
- Shapes often only set `SortOrder1`; comment in vanilla: `SortOrder2` assigned in code to keep shape order consistent per material.

### Variant Helpers

```xml
<block name="ironDoorBlockVariantHelper">
  <property name="Extends" value="ironDoorGrey" />
  <property name="ItemTypeIcon" value="all_blocks" />
  <property name="DescriptionKey" value="ironDoorBlockVariantHelperDesc" />
  <property name="SelectAlternates" value="true" />
  <property name="PlaceAltBlockValue" value="ironDoorGrey,ironDoorWhite,..." />
  <property name="SortOrder1" value="U200" />
  <property name="SortOrder2" value="0000" />
  <property name="FilterTags" value="MC_playerBlocks,SC_playerHelpers" />
</block>
```

Behavior:

- `SelectAlternates=true` + CSV `PlaceAltBlockValue` = R-menu / shape-style alternate picker for those blocks.
- Helper usually sits at `U200`+ so it appears in the player-helper bucket.
- Individual color blocks keep their own `B###` / family sort so they still order correctly if shown directly.
- Helper `Extends` a representative member for shared stats/sounds/materials; often overrides description / creative / filters.
- Common: `param1="CustomIconTint"` on helper extends so the helper icon isn’t stuck with a tinted child look (see DecorationBlockPlus generators).

Alt list order in `PlaceAltBlockValue` is the order players cycle; sort order of the *helper itself* is independent of that CSV order.

## 8. Flatten recipe (decoration / mod clones)

Goal: produce a self-contained `<block>` that behaves like the engine’s resolved form, without depending on a parent that you are about to change or hide.

### Correct flatten algorithm

1. Resolve parent recursively (cache flattened parents).
2. From parent props, **remove**:
   - `CreativeMode` (always)
   - every name in child’s `Extends/@param1` (comma-split, trim)
   - optionally drop `Extends` itself from the output
3. Overlay child properties (child wins).
4. Property **classes** (`RepairItems`, `UpgradeBlock`, …): treat class name as an excludable unit; support `Class.Nested` exclusions if you need parity with engine.
5. Drops:
   - Start with child drops.
   - If no `dropextendsoff`, merge parent drops where `(event, name)` not already present.
   - Strip `dropextendsoff` from output.
6. Explicitly set on every new mod block:
   - `CustomIcon` (and tint if needed)
   - `CreativeMode` (do not rely on inheritance)
   - `SortOrder1` / `SortOrder2` for list placement
7. If creating a VariantHelper, also set `SelectAlternates`, `PlaceAltBlockValue`, `DescriptionKey`, `ItemTypeIcon`, helper `FilterTags`, and a `U###` sort bucket.

### Flatten script status (fixed)

`00_DLL-Projects/Generators/DecorationBlockPlus/flatten_blocks.py` now matches engine rules for:

- Extends `param1` CSV exclusions (read from the Extends property)
- Always-exclude `CreativeMode`
- Property-class + nested `Class.Child` exclusions
- `dropextendsoff` + drop merge by `(event, name)`

`flatten_blocks_doorsecure.py` imports that shared logic.

Decoration output still intentionally strips drops / `RepairItems` / `UpgradeBlock` from written XML (`STRIP_*` flags).

### Thin vs full flatten

| Approach | When |
|---|---|
| Keep `Extends` + overrides only | Vanilla-style; parent stays stable |
| Full flatten (no Extends) | You need a clone that survives parent xpath mods / material rewrites / decoration “make placeable” transforms |
| Flatten then re-extend a local master | Good for AGF wood/iron/steel families sharing repair/upgrade |

## 9. Quick reference cheat sheet

```
Extends.value          → direct parent name (must exist already)
Extends.param1         → EXCLUDE these inherited props/classes
CreativeMode           → NEVER inherited; unset ⇒ All
dropextendsoff         → do not copy parent drops
drop merge             → child names win; parent adds missing names per event
CustomIcon             → sprite name; else block name; required for new names
CustomIconTint/TintColor → hex color for icon / mesh tint variants
SortOrder              → SortOrder1 + SortOrder2, ordinal string sort
VariantHelper          → SelectAlternates + PlaceAltBlockValue CSV + usually U### sort
param1 elsewhere       → NOT exclusion; property secondary arg
```
