# 7D2D v3.3 — Inventory, toolbelt, and storage (researched)

**Compared:** public 3.2 copy vs experimental 3.3 client  
**Researched:** 2026-10-01  
**3.2 install:** `C:\Program Files (x86)\Steam\steamapps\common\7 Days to Die - 3.2` (Steam build `24994517`, beta `public`, copied before the client was switched)  
**3.3 install:** `C:\Program Files (x86)\Steam\steamapps\common\7 Days To Die` (Steam build `25542620`, beta `latest_experimental`)  
**Sources:** vanilla `Data/Config` on both installs, and `Assembly-CSharp.dll` method diffs plus decompiles of `ToolbeltConfig`, `ToolbeltFromXml`, `XUiC_ToolbeltWindow`, `XUiC_Toolbelt`, `XUiC_Backpack`, `EntityPlayer` bag methods, and `Inventory`

Use this when checking a mod for 3.3. Do not re-diff the whole game. Confirm the mod’s xpaths and Harmony targets against the lists below.

## How a mod should branch

XML, same pattern already used in this repo:

```xml
<if cond="game_version() &lt; version(1,3,30)">
	<!-- 3.0 through 3.2 -->
</if>
<if cond="game_version() &gt;= version(1,3,30)">
	<!-- 3.3 and later until these systems change again -->
</if>
```

`game_version()` is `Constants.cVersionInformation.Version`, and that object is not `3.3`. Both 3.2 and 3.3 build it as `new Version((int)ReleaseType, Major, Minor, Build)`. `EGameReleaseType.V` is 1. Display minor is `Minor / 10` and `Minor % 10`, so 3.2.0 is minor 20 and 3.3.0 is minor 30. This 3.3 client is `Version(1, 3, 30, 17)` (`V 3.3.0 (b17)`). `version(3,3)` is `Version(3, 3)`, which is greater than `1.3.30`, so `game_version() < version(3,3)` stays true on 3.3 and the 3.3 branch never runs. Compare with `version(1,3,30)`.

`game_version` is a real conditional in 3.3 (`mod_loaded`, `game_version`, `xpath`, and the other usual evaluators are still in the patcher). A failed child xpath makes the patcher log `WRN XML patch ... did not apply` for the child and again for the `<conditional>` that contains it.

C# reads `Constants.cVersionInformation` (`Major`, `Minor`, `LongString`), with `cVersionMajor` / `cVersionMinor` as the fallback. The encoded minor is 0, 10, 20, 30 for 3.0 through 3.3, so a 3.3 check is `Minor >= 30`. `Minor >= 3` is true on 3.2 as well. If the version cannot be read, treat “`ToolbeltConfig` exists and `Inventory.PUBLIC_SLOTS_PLAYMODE` does not” as 3.3.

One DLL can ship for every v3. Compile 3.3-only types through reflection. A direct reference to `ToolbeltConfig` in a method that gets JIT’d on 3.2 will fail to load that method.

## Official notes that matter here

From the experimental notes that match what is in the files:

- Multiple toolbelt pages for the prefab editor. New `toolbelt.xml` sets slots, bars, and pages.
- Inventory size increases from equipped backpack items.
- `ItemActionRanged.TryExecuteAction` is now virtual.
- Item background no longer flickers when moving into storage.
- Moving a stack no longer plays both pickup and place sounds.

A backpack mod that does `triggered_effect[@value='27']` misses on 3.3. That value is now 32. The cvar name `.carryCapacityBase` is still there.

`EntityPlayer.CalcCurrentBackpackSize` takes `PassiveEffects.BagSize` (default 45 in code if the effect is missing), includes equipment, then clamps to `MaxBagSize` (1 through 96). `UpdateBagpackSize` resizes the bag. Shrinking compacts it, keeps death-keep items in the remaining slots when it can, and drops the overflow.

Worn backpacks **add** slots. They do not replace `BagSize`. A mod `base_set` of 60 plus a large backpack’s `base_add` still stacks, then the 96 cap applies.

Each tick:

- `CarryCapacity` comes from `PassiveEffects.CarryCapacity` (base 0, so the cvar and perks supply it)
- `_encumberedslots` = used slots past `CarryCapacity`
- `_encumbrance` = that count divided by (`bag.SlotCount - CarryCapacity`)

`XUiC_Backpack.SetStacks` sets `AttributeLock` on slots at index `>= CarryCapacity`. The UI slot count is `bag.SlotCount`. If that is greater than the number of `item_stack` controllers, the game logs a warning and the extra slots have no cell.

## Toolbelt

New file, 3.3 only: `Data/Config/toolbelt.xml`.

```xml
<editorconfig>
	<slots slot_per_bar="10" bar_per_page="2" page_count="1" />
</editorconfig>
```

`ToolbeltFromXml.Load` reads **only** `editorconfig`. The comment in the file says `gameconfig` is unsupported, and the loader never parses it. Code defaults on `ToolbeltConfig` are `SlotsPerBar = 10`, `BarsPerPage = 1`, `PageCount = 1`. The XML loader clamps slots per bar to 1–10, bars per page to 1–2, and pages to 1–10. The warning condition is `value < 1 && value > 10`, which never fires. `Math.Clamp` still enforces the range.

`ToolbeltConfig.CurrentConfig` returns `EditorConfig` while the prefab editor is active, otherwise `GameConfig`. `TotalSlots = SlotsPerBar * BarsPerPage * PageCount`. Play mode is therefore 10 slots, 1 bar, 1 page, until a mod changes `GameConfig`. A 12-slot player belt cannot be done in `toolbelt.xml`. Set `GameConfig.SlotsPerBar` from code. The property itself is not clamped. Do that before `EntityPlayer.InitInventory`, which does `new Inventory(this, ToolbeltConfig.CurrentConfig.TotalSlots)`. `Inventory.ReadInto` then resizes the saved grid to that `SlotCount`. `Inventory.SlotCount` has no setter. `ChangeSlotCount` changes the count **inside** a slot, not the number of slots.

`windowToolbelt` is still `controller="ToolbeltWindow"`. 3.3 size is width 753, pos `-376, 84`. The old fixed grids are gone.

3.2 names that **do not exist** on 3.3:

- `grid[@name='inventory']` and `grid[@name='inventory2']`
- `button[@name='btnClearInventory1']` and `btnClearInventory2`

3.3 structure:

- `rect/rect[@controller='Toolbelt']/rect[@name='bars']` with `repeat_count="{%beltCount}"`
- child `rect[@name='bar${repeat_i}']`
- `grid[@name='inventory${repeat_i}']` with `cols="{%beltslots}"`
- `button[@name='btnClearInventory${repeat_i}']` at `800,-32`
- pager `toolbeltPager` (`btnToolbeltPrev`, `btnToolbeltNext`, `{toolbeltpage}`), visible `{showpager}`

Bindings on `XUiC_Toolbelt` read `ToolbeltConfig.CurrentConfig`: `beltslots`, `beltCount`, `toolbeltpage`, `showpager`. Hardcoding `cols` to 12 overrides the editor’s own slot count. Leave `cols` on the binding and set `GameConfig.SlotsPerBar` from the DLL.

XP bar sprite is still `rect/sprite[@type='filled'][@width='750']`. Window `@pos` and `@width` still exist. For 12 slots at 75px, width 903 and pos `-452,84` match the 3.3 vertical position. The clear button moves to `950,-32`.

`XUiC_ToolbeltWindow.BtnClearInventory_OnPress(int barIndex)` clears `SlotsPerBar` slots starting at `page * SlotsPerPage + bar * SlotsPerBar`. The 3.2 methods `BtnClearInventory1_OnPress` and `BtnClearInventory2_OnPress` are gone. Once `SlotsPerBar` is 12, the vanilla clear covers the extra slots. The old postfix that called `EmptyToolbelt(10, 12)` must not be patched on 3.3.

Removed on 3.3, still the 3.0–3.2 hook for a wider play belt:

- `Inventory.get_PUBLIC_SLOTS_PLAYMODE`
- `Inventory.get_SHIFT_KEY_SLOT_OFFSET`
- `Inventory.get_PUBLIC_SLOTS`
- `Inventory.get_PUBLIC_SLOTS_PREFABEDITOR`

Still present on 3.3, so the slot 11 and 12 key patches can stay: `PlayerActionsLocal` `InventorySlotWasPressed`, `CreateActions`, and the options-control create/save/load methods. `Inventory` itself was rewritten (115 methods down to 78). Do not assume other `Inventory` members survived. Confirmed gone from the player inventory type: `GetSlots`, and the old public-slot getters.

## Loot and container UI

`windowLooting` and `windowBagStorage` still exist. Their `grid[@name='queue']` moved under `rect[@name='content']/scrollview`. Controllers are still `LootContainer`.

3.2 xpaths that fail on 3.3:

- `/windows/window[@name='windowLooting']/rect[@name='content']/grid[@name='queue']`
- `/windows/window[@name='windowBagStorage']/grid[@name='queue']`

3.3 loot window width is `{% v2i_x(gridDimensions) * 75 + 16 }`. The grid is still 9 columns by 10 rows at cell 75, inside the scroll view. Bag storage grid is 10 by 15 at cell 75. Header anchors that said `queue` now say `scrollbarborder`.

A failed `set`/`remove` can abort the rest of that patch file. Gate the old grid xpaths with `game_version() < version(1,3,30)` instead of letting them miss. Decoration Block and Larger Storage Option both force that loot `queue` to 15×15; those two sets are inside that conditional. There is no 3.3 equivalent. The crate `loot.xml` sizes still apply, and 3.3 scrolls the container.

Writable crates, 15 shapes, 3× health, break-to-pickup. Slot counts from its `loot.xml`:

|---|---|---|---|

## When checking the next mod

1. Search its XML for `windowToolbelt`, `inventory2`, `btnClearInventory1`, `windowBackpack`, `windowLooting`, `windowBagStorage`, `grid[@name='queue']`, `grid[@name='inventory']`.
2. Search its C# for `PUBLIC_SLOTS`, `GetSlots`, `BagSize`, `CarryCapacity`, `TEFeatureStorage`, `OnLockedServer`, `BtnClearInventory`.
3. If a hit is in the tables above, branch with `game_version()` or `Prepare()`. Do not copy a 3.2 xpath forward and hope the patcher skips a miss.
4. `MaxBagSize` 96 is enforced in code. Raising `BagSize` in XML above 96 does not raise the cap.
5. Player toolbelt width above 10 is a code change to `GameConfig.SlotsPerBar`, not an edit to `toolbelt.xml`.

`ITileEntityLootable` is gone. `TEFeatureStorage` still exists. On 3.3 it implements `IInventory` and holds an `ItemStackGrid` (`ItemGrid`, `PlayerOwned`, `SlotLocks`, `IsLocked`, `items`). `UpdateSlot`, `TryStackItem`, `AddItem`, `IsEmpty`, and `SetModified` are still on `TEFeatureStorage` in both versions.

`LockEntry` is no longer a top-level class. 3.3 nests it as a private struct `LockManager.LockEntry` with field `Target`. `singleLocks` and `sharedLocks` are still on `LockManager`. `UnlockRequestServer` is now `(int _playerId, bool _isForceUnlocked)`.

`Bag.GetSlots` is gone on 3.3. Slots are `Bag.ItemGrid.items`. `Bag.SetSlots(ItemStack[], bool)` and `Bag.SetSlot(int, ItemStack)` replace the 3.2 signatures. `LockedSlots` is still the lock array.

A direct field or method typed as `ITileEntityLootable` or top-level `LockEntry` still fails assembly load on 3.3. Do not leave those names in a DLL that also has to load on 3.3.

`ItemStack.itemValue` is a field on 3.2 and a property (`itemValueField` behind it) on 3.3. `ItemStack.count` is the same split (`countField` on 3.3). A DLL compiled against either field throws `MissingFieldException` the first time that method is JIT'd. On the 07:50 save load the `itemValue` field failed inside `XUiC_ItemStack.GetBindingValueInternal` while the combine window was parsing, and `XUi.CalloutWindow` stayed null. `PlayerMoveController.Update` then null-ref'd that field every frame (IL offset `0x469`). On the 08:05 load, selecting a backpack item threw `Field not found: int .ItemStack.count` from Open All's postfix on `XUiC_ItemActionList.AddActionListEntry`. `TEFeatureStorage.bPlayerStorage`, `bTouched`, `worldTimeTouched`, and `bWasTouched` are gone. 3.3 uses `ItemGrid.PlayerOwned`, `ItemGrid.Touched`, and `ItemGrid.WorldTimeTouched`.
